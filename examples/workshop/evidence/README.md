# Evidence for case QUILLDROP

The workshop investigates **synthetic** evidence generated by
[`fsagen`](https://github.com/aoiflux/fsagen). Nothing here is real, nothing is
malicious, and the whole corpus comes back from a seed.

> **No version is pinned.** The build scripts ask `fsagen features --json`
> for each feature the playbook uses and stop, naming it, when one is
> missing. fsagen v0.4.0 was the first release with all of them. A newer
> generator version writes other bytes for the same seed, so everyone in the
> room should build with the same release. The contract below is what the
> corpus has to satisfy, and it is satisfied on NTFS — see *Two environment
> hazards* for what ext4 and APFS cost you.

## Why synthesized evidence

1. **It is legal and shareable.** Real triage collections carry real user data.
2. **It fits on a USB stick.** The case tree is a few megabytes, and the disk
   image is 64 MiB.
3. **It comes back.** `--seed 88412` produces the same bytes on every laptop.

## Build it

```
go install github.com/aoiflux/fsagen@latest

.\examples\workshop\evidence\build_evidence.ps1                 # Windows, everything
./examples/workshop/evidence/build_evidence.sh                  # Linux / macOS
```

The scripts check fsagen's features first and then build four topics, each
from its own playbook and all with `--seed 88412`. Pick some with
`-Topic timestomp,ads,registry` (PowerShell) or `--topic timestomp,ads,registry`
(sh); without one they build all four.

| Topic | Playbook | Writes | Read by |
|---|---|---|---|
| `timestomp` | `topics/timestomp.playbook.yaml` | `case_quilldrop.img`, a GPT disk image | `dfrws/1_timestomp` |
| `case` | `quilldrop.playbook.yaml` | `case/` and `case_quilldrop.body`, the whole case | the ten beats |
| `ads` | `topics/ads.playbook.yaml` | Chrome `History` (the redirect hops) and `Cookies`, in `case/` | `dfrws/2a_ad_redirects`, `dfrws/2b_ad_cookies` |
| `registry` | `topics/registry.playbook.yaml` | `NTUSER.DAT` (the Run key), in `case/` | `dfrws/3_run_keys` |

`quilldrop.playbook.yaml` tells the whole case. Each topic playbook copies
the few steps of it that one deep dive needs, unchanged, so a topic builds on
its own. `sweep/workshop_topics_test.go` fails if a topic's copy drifts from
the case.

`ads` and `registry` write into `case/` at the paths the case tree uses, so
the dfrws programs read them without a change. The case tree already holds
those files, so after a case build that worked they are skipped. After one
that failed they fill in. Neither holds an executable. Defender scans the
image as one file, not the files inside it. So
`-Topic timestomp,ads,registry` builds every deep dive's input on a machine
with Defender on, with no exclusion.

The same commands by hand:

```
fsagen --seed 88412 --playbook examples/workshop/evidence/topics/timestomp.playbook.yaml \
       --clean --image examples/workshop/case_quilldrop.img --image-fs ntfs \
       --image-size 64M --partition gpt --image-time 2026-03-12T06:00:00Z

fsagen --seed 88412 --playbook examples/workshop/evidence/quilldrop.playbook.yaml \
       --timeline examples/workshop/case_quilldrop.body \
       --timeline-format bodyfile --timeline-source modelled \
       --on-unsupported=skip \
       examples/workshop/case

fsagen --seed 88412 --playbook examples/workshop/evidence/topics/ads.playbook.yaml \
       --into-existing --meta examples/workshop/case.ads.fsagen examples/workshop/case

fsagen --seed 88412 --playbook examples/workshop/evidence/topics/registry.playbook.yaml \
       --into-existing --meta examples/workshop/case.registry.fsagen examples/workshop/case
```

`--timeline-source modelled` is not optional. The `observed` timeline reports
inode numbers and whatever else touched the tree, so it is reproducible only on
one machine — and it omits deleted objects, which beat 6 depends on.

## What the steps expect to find

Paths are relative to `examples/workshop/case/`. Change one and you break a
step.

| Path | What it has to be | Read by |
|---|---|---|
| `Finance/*.xlsx.enc` (≥3) | high-entropy content, so `fs_entropy` reads above 7.9. **Not `.xlsx`**: fsagen v0.1.0 refuses to fill a name that promises an OOXML spreadsheet, and both escapes it offers write text, which cannot clear 7.9. `.enc` is what an encrypted spreadsheet looks like on disk in any case. Measured 7.997 on the 64 KiB exhibits the playbook writes | 1 |
| `Users/clerk/Inbox/invoice.eml` | real RFC 5322, one http(s) link, one attachment named `Invoice_88412.pdf.exe` | 2 |
| `Users/clerk/Downloads/Invoice_88412.pdf.exe` | a PE, plus a Mark-of-the-Web whose `HostUrl` host equals the email link's host | 3 |
| `Users/clerk/AppData/Local/Google/Chrome/User Data/Default/History` | Chrome history containing that same URL. For `dfrws/`, a redirect chain ends at the lure page and leads back through `from_visit` to an ad click, with the server-redirect bit (`0x80000000`) set on each hop after the click | 3, `dfrws/2a_ad_redirects`, `dfrws/2b_ad_cookies` |
| `Users/clerk/AppData/Local/Google/Chrome/User Data/Default/Network/Cookies` | Chrome's cookie database, holding cookies from the ad hosts in that chain and from at least one host the history never visited | `dfrws/2b_ad_cookies` |
| `Users/clerk/NTUSER.DAT` | a regf hive whose `Software\Microsoft\Windows\CurrentVersion\Run` key names `updater.exe` | `dfrws/3_run_keys` |
| `Users/clerk/AppData/Roaming/SyncAgent/updater.exe` | a PE with `TimeDateStamp` zero and at least two imported DLLs | 4, 9 |
| `Users/clerk/AppData/Local/Temp/bkp_20260311.zip` | ≥12 members whose dates predate the archive; then backdated so `mtime` lands in 2024 while `crtime` stays at its true 2026 value | 6, 7, 9 |
| `Users/clerk/AppData/Local/Temp/staging/…` | deleted — present in the modelled bodyfile, absent on disk | 6 |
| `Users/clerk/AppData/Roaming/persistence.reg` | a `.reg` text export writing a Run key naming `updater.exe` | 1 |

One more input sits beside `case/` rather than in it:
`examples/workshop/case_quilldrop.img`, a GPT disk image laid out as Windows
Setup lays out a system disk: an EFI system partition, a Microsoft reserved
partition, the Windows (basic data) NTFS volume, and a recovery partition.
The Windows volume holds the timestomp topic's part of the case: the clerk's
documents, `updater.exe`, and the staging files with the archive built from
them. In the Windows volume:

- `updater.exe`'s `$STANDARD_INFORMATION` creation time is earlier than its
  `$FILE_NAME` one;
- `bkp_20260311.zip`'s `$STANDARD_INFORMATION` change time ("MFT modified") is
  when its modification time was backdated, after the creation time it kept;
- the change journal (`$Extend\$UsnJrnl`) records each operation at the time it
  ran, never the time the stomp wrote, including a `BasicInfoChange` for both
  stomps.

`dfrws/1_timestomp` reads the image and writes
`examples/workshop/case_quilldrop.mft` beside it, a copy of each volume's
`$MFT` in turn. Both are gitignored. So are fsagen's run records:
`case.fsagen/`, `case_quilldrop.img.fsagen/`, `case.ads.fsagen/` and
`case.registry.fsagen/`.

Until the evidence is built, a `dfrws/` program whose input is absent prints its
"missing" line.

Two rules on the bodyfile:

- The `name` column comes out **absolute, with forward slashes**, and that is
  fine. fsagen v0.4.0 has no flag to make it relative, and
  `quilldrop.path` joins it on with `str_format("%s/%s", root, name)`, so an
  absolute name becomes `examples/workshop/case//Users/…` — a doubled
  separator, which Windows and POSIX both collapse. Measured: 136 rows, 12 of
  them deleted, and step 6 reports exactly those 12 as absent. Were absolute
  names breaking `fs_exists`, all 136 would have been reported missing.
- The modelled timeline must carry the deleted staging paths.

## Two environment hazards, both real

- **Windows Defender refuses generated PE files.** fsagen's own acceptance test
  records it flagging a generated implant as `Trojan:Win32/Bearfoos.B!ml`, and
  its verdict is not stable — it allowed and then refused identical bytes
  minutes apart. This is why the implant is `updater.exe` and not `svchost.exe`.
  A refusal stops the case-tree run at the file refused, so every later step
  is missing, the Run key and the timestomp among them. The disk image is not
  affected. The build then fills in the `ads` and `registry` topics, so the
  four deep dives still have their input. The ten beats need the whole tree:
  add a Defender exclusion for `examples/workshop` before the workshop.
- **Windows Search rewrites `.eml` files.** In an indexed folder it attaches an
  `OECustomProperty` stream within seconds. Generate outside indexed locations.

The Mark-of-the-Web and the alternate data stream are NTFS features, and beat 3
reads both. A birth time is not: `crtime` belongs to the **volume** rather than
to the operating system, and `ctime` is POSIX and is read everywhere. What is
measured below is one volume, **WSL ext4**, where every birth time came back 0
so beat 6's finding could not fire. **APFS is unmeasured** -- it keeps a birth
time and fsagen reads one there, so do not assume a Mac loses the beat; the
build scripts test the timeline they have just written and will say so on the
day. **Generate on NTFS, or take the pre-built corpus** -- see *Where the
pre-built corpus comes from*, below. Same seed, same playbook, the fsagen
v0.4.0 release binaries, measured 2026-10-12 on a Windows 11 NTFS volume and on
WSL ext4. On NTFS the two generated PEs were written under other names, so
Defender had nothing to refuse; no file or row count depends on the names:

| | NTFS | ext4 |
|---|---|---|
| `build_evidence` with no `--on-unsupported` | exit 0 | **exit 1, and no corpus at all** |
| with `--on-unsupported=skip`, which both scripts now pass | exit 0 | exit 0, each skip recorded in `case.fsagen/run-manifest.json` |
| files generated | 100 | 100 |
| rows in the modelled timeline | 136 | 135 |
| the row that is missing | — | `Invoice_88412.pdf.exe:Zone.Identifier` |
| rows whose `crtime` is 0 | 0 | **135 of 135** |
| rows where `mtime < crtime` — **beat 6's finding** | **1** | **0** |
| deleted rows in the timeline | 12 | 12 |

Beat 3's ADS line reporting nothing is the honest answer, as it always was.
Beat 6 is the one that costs: `06_lies.mut:8` asks whether a file's `mtime`
precedes its `crtime`, and with every `crtime` at 0 the answer is no for every
row, so **the beat's whole anti-forensics finding silently does not fire** — no
error, one fewer line. Its other half, the twelve deleted staging files, works
on both. The build scripts test the timeline they have just written and say so
when this happens, which is a measurement rather than a guess about the
filesystem, so it is also right on ReFS, on FAT32 and on a network share.

## Where the pre-built corpus comes from

It is the same corpus these scripts generate, built once on NTFS and handed out
so that nobody's machine has to produce it. Three things travel together:

- the case tree, `examples/workshop/case/` -- **100 files**;
- the modelled timeline the beats read, `examples/workshop/case_quilldrop.body`
  -- **136 rows**;
- `SHA256SUMS`, in the format `sha256sum -c` reads, which is the convention
  `case_bundle` writes in this same toolchain.

**Ask your presenter for it.** It ships as a checksummed asset beside the Mutant
release this workshop pins, and the presenter brings it on a stick as well,
because a room of laptops on conference wifi is not a download plan. No filename
is printed here on purpose: the asset is named in the release it travels with,
and a name written here would go stale the first time it changed.

Check it before you trust it -- checking things is the whole session:

```
sha256sum -c SHA256SUMS                     # Linux, macOS, Git Bash
```

```
Get-FileHash -Algorithm SHA256 <file>       # PowerShell, compare by eye
```

Every line must say `OK`. If one does not, you are holding a different corpus
from the rest of the room, and the three exhibit digests step 9 prints will not
match the run sheet.

**If nobody gave you one**, generate it. `build_evidence.ps1` on NTFS is the path
every number above is measured against, and on another volume the scripts still
build a corpus and tell you what it cost.

## What is reproducible, and what is not

The corpus is byte-identical across machines for one fsagen version, one seed
and one playbook. So are the three exhibit digests step 9 prints.

The **manifest** step 9 writes is not, and must not be. It records when the case
was opened, when each exhibit was registered, how long the examination took and
when the seal was signed. Two examinations are two events. A tool that gave you
one number for both the evidence and the custody would be lying about one of
them — and which one it lies about is the thing you would be cross-examined on.
